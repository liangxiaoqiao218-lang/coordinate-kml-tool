# Release Identity Specification

## Status

```text
Specification status: DESIGN
Implementation status: NOT STARTED
Secondary deployment: NOT APPROVED
Primary Production: BLOCKED
```

This specification defines a non-sensitive, machine-readable identity for every
GeoKit Lab build and deployment. It does not authorize deployment or modify the
current `/api/version` implementation.

## 1. Purpose

Release Identity answers, with recorded evidence:

- which source commit produced the running application;
- which immutable artifact was built from that source;
- which release label governs the artifact;
- when the artifact was built;
- where and when it was deployed;
- whether Primary and Secondary run the intended release.

An arbitrary application version string is not sufficient. A valid identity
must bind source, artifact, release, and deployment facts without exposing
credentials or runtime configuration values.

Release Identity is required for:

- deployment approval;
- production incident investigation;
- rollback selection;
- Primary and Secondary synchronization checks;
- controlled cohort observation;
- payment and entitlement releases;
- Coordinate Engine and UTM V2 migration decisions.

## 2. Identity Model

Release Identity contains two layers.

### 2.1 Build identity

Build identity is immutable for the lifetime of an artifact:

- `releaseVersion`;
- `gitCommit`;
- `artifactHash`;
- `buildTime`;
- optional build-system identifier.

It must be generated by the governed build process from a clean, exact source
commit. It must not be recomputed from mutable files in a running instance.

### 2.2 Deployment identity

Deployment identity describes where the immutable artifact is running:

- `environment`;
- `deploymentTime`;
- optional non-sensitive deployment identifier.

Primary and Secondary should deploy the same immutable artifact. Their
`environment`, `deploymentTime`, and platform deployment identifiers may differ.
Runtime environment variables must not alter the build identity.

## 3. Required Fields

| Field | Type | Required | Source | Rule |
|---|---|---:|---|---|
| `schemaVersion` | string | yes | specification/build | Fixed schema identifier |
| `environment` | string | yes | deployment configuration | Controlled enum; never inferred from hostname alone |
| `releaseVersion` | string | yes | release manifest | Human-readable governed release or RC label |
| `gitCommit` | string | yes | build system | Full 40-character Git commit hash |
| `artifactHash` | string | yes | build system | SHA-256 or governed immutable image digest |
| `buildTime` | string | yes | build system | UTC ISO 8601 timestamp |
| `deploymentTime` | string | yes | deployment system | UTC ISO 8601 timestamp |

Recommended fields:

| Field | Type | Purpose |
|---|---|---|
| `deploymentId` | string | Non-sensitive platform deployment reference |
| `buildId` | string | CI/build-system reference |
| `sourceBranch` | string | Audit aid; commit remains authoritative |
| `runtimeVersion` | string | Major runtime identity, for example Node.js version |
| `status` | string | Deployment lifecycle state such as `active` or `rollback` |

### 3.1 Controlled values

`environment` must use an approved value:

```text
development
staging
secondary
primary
```

`releaseVersion` must be assigned through the Release Manifest. Examples:

```text
v1.2.0
v2.0.0-rc.1
coordinate-engine-v2-rc1
```

The release label is descriptive. `gitCommit` and `artifactHash` are the
technical authorities.

### 3.2 Artifact hash definition

The release process must choose and document one canonical artifact identity:

- SHA-256 of a deterministic application bundle; or
- immutable container image digest; or
- immutable platform artifact digest supplied by the deployment system.

The hash must identify the exact deployable artifact, not a source directory,
working tree, selected file list, or post-deployment filesystem snapshot.

## 4. Schema

Required response schema:

```json
{
  "schemaVersion": "release_identity_v1",
  "environment": "secondary",
  "releaseVersion": "coordinate-engine-v2-rc1",
  "gitCommit": "095168fc44b697ab11f8e4af2277704e9bd240cc",
  "artifactHash": "sha256:<64-lowercase-hex-characters>",
  "buildTime": "2026-08-08T00:00:00Z",
  "deploymentTime": "2026-08-08T00:30:00Z"
}
```

Example values are illustrative and must not be treated as a deployment record.
In particular, the example `artifactHash`, build time, and deployment time do
not assert that an artifact exists.

Extended response example:

```json
{
  "schemaVersion": "release_identity_v1",
  "environment": "secondary",
  "releaseVersion": "coordinate-engine-v2-rc1",
  "gitCommit": "095168fc44b697ab11f8e4af2277704e9bd240cc",
  "artifactHash": "sha256:<64-lowercase-hex-characters>",
  "buildTime": "2026-08-08T00:00:00Z",
  "deploymentTime": "2026-08-08T00:30:00Z",
  "deploymentId": "<non-sensitive-platform-deployment-id>",
  "buildId": "<ci-build-id>",
  "sourceBranch": "v2/utm-intent-router",
  "runtimeVersion": "node-<major.minor.patch>",
  "status": "active"
}
```

## 5. API Exposure Rules

### 5.1 Endpoint

`GET /api/version` must return the Release Identity schema for the running
deployment.

The endpoint must:

- be read-only;
- require no user credential for basic deployment verification;
- return JSON with a stable content type;
- identify the running artifact, not merely a static source string;
- use build and deployment metadata supplied by governed automation;
- return the same build identity on every instance of the same artifact;
- return the correct deployment identity for the current environment;
- be safe for monitoring, smoke tests, and support diagnostics.

### 5.2 Backward compatibility

During migration, the current `version` field may be retained as a deprecated
additive compatibility field:

```json
{
  "version": "2026-05-01-quota-contact-v2",
  "schemaVersion": "release_identity_v1",
  "environment": "secondary",
  "releaseVersion": "coordinate-engine-v2-rc1",
  "gitCommit": "<full-commit>",
  "artifactHash": "sha256:<artifact-digest>",
  "buildTime": "<utc-build-time>",
  "deploymentTime": "<utc-deployment-time>"
}
```

Existing clients must not break when the new fields are added. The deprecated
field must not remain the sole deployment identity after the migration period.

### 5.3 Failure behavior

Missing required identity metadata is a release-governance failure. The endpoint
must not invent values, inspect an unavailable `.git` directory and guess, or
substitute `unknown` while allowing the deployment to be treated as approved.

Permitted pre-production behavior is to expose an explicit incomplete state,
for example:

```json
{
  "schemaVersion": "release_identity_v1",
  "identityStatus": "incomplete"
}
```

A deployment with incomplete identity cannot satisfy Secondary or Primary
readiness.

### 5.4 Cache behavior

Version responses must not be served from a stale cross-deployment cache. The
deployment design must define cache-control behavior so a validation request can
observe the currently active artifact after deployment or rollback.

## 6. Security Rules

The endpoint and manifest must never expose:

- API keys or authorization headers;
- environment variable values;
- Supabase service-role keys or database credentials;
- payment credentials, merchant identifiers not approved for public display, or
  callback secrets;
- user, order, entitlement, quota, or coordinate data;
- filesystem paths, home directories, or workspace paths;
- internal network addresses;
- stack traces or provider request payloads;
- private repository URLs containing credentials;
- complete environment dumps.

Release Identity fields are non-secret deployment metadata. Even so:

- allow only schema-defined fields;
- normalize and validate every value;
- reject control characters and unbounded strings;
- do not merge arbitrary environment objects into the response;
- do not use request parameters to select identity values;
- keep detailed build logs in governed internal storage, not `/api/version`.

`artifactHash` proves identity against an approved manifest. It is not a secret
and is not, by itself, proof that an artifact is safe.

## 7. Build and Deployment Generation Rules

### 7.1 Build phase

The governed build process must:

1. require a clean source checkout at an exact commit;
2. assign the release version from an approved Release Manifest;
3. record the full Git commit;
4. build once;
5. generate the canonical artifact hash or capture the immutable image digest;
6. record UTC build time and build ID;
7. create a non-secret build identity file or equivalent immutable metadata;
8. verify no credentials or local environment files enter the artifact;
9. retain the artifact and manifest for deployment and rollback.

The artifact must not calculate its own artifact hash after unpacking unless the
hashing specification explicitly defines that representation.

### 7.2 Deployment phase

The governed deployment process must:

1. select an existing approved immutable artifact;
2. set the controlled `environment` value;
3. record deployment time and deployment ID;
4. preserve the build identity unchanged;
5. verify `/api/version` after activation;
6. compare the response against the approval record;
7. stop validation when any required identity differs;
8. record the previously active artifact as the rollback target.

No operator may edit Release Identity fields manually in the running service.

## 8. Deployment Governance

### 8.1 Primary and Secondary alignment

Primary and Secondary are two deployment roles for one product, not separate
code products.

For a synchronized release:

- `releaseVersion`, `gitCommit`, `artifactHash`, and `buildTime` must match;
- `environment`, `deploymentTime`, and `deploymentId` may differ;
- runtime secrets and environment-specific configuration may differ only within
  approved governance rules;
- both identities must be recorded in the Production Release Manifest.

Code must not be rebuilt separately for Primary after Secondary validation. The
same validated immutable artifact should be promoted. If rebuilding is
unavoidable, the new artifact requires a new identity and revalidation.

### 8.2 Approval evidence

Before Secondary deployment approval:

- the candidate artifact identity must exist;
- the current Secondary identity and rollback artifact must be recorded;
- the approved artifact identity must match the deployment selection.

Before Primary release approval:

- the validated Secondary artifact identity must be recorded;
- the Primary target and rollback identity must be recorded;
- the artifact promoted to Primary must match the validated artifact;
- required validation, approval, and rollback evidence must be complete.

### 8.3 Rollback

Rollback must select a previously recorded immutable artifact. After rollback,
`/api/version` must return the rollback artifact's build identity and the new
rollback deployment identity. A successful health response with the wrong
identity is a failed rollback.

## 9. Migration and Commercial Release Rules

### 9.1 Coordinate Engine and UTM V2

Every Coordinate Engine or UTM V2 candidate, controlled cohort, migration
decision, and production release must reference:

- release version;
- full Git commit;
- artifact hash;
- environment;
- build and deployment time;
- rollback artifact identity.

`HOLD_LEGACY` remains authoritative until the approved Release Identity is bound
to the required cohort, Export Compare, rollback, and migration approval
evidence. A matching commit alone does not approve migration.

### 9.2 Payment, user, order, and entitlement releases

Payment and entitlement changes must be bound to a Primary Release Identity and
Production Release Manifest. Secondary must keep payment disabled unless a
separate, explicitly governed sandbox design is approved.

Support and incident records involving quota, VIP, orders, or payments must
include the observed Release Identity. Do not diagnose commercial behavior from
a hostname or human-readable version string alone.

## 10. Validation Requirements

Implementation of this specification requires tests for:

- schema field presence and validation;
- full commit and artifact hash formats;
- build identity immutability across instances;
- correct Primary/Secondary environment identity;
- backward-compatible `version` field during transition;
- absent-secret and allowlisted-field behavior;
- incomplete metadata blocking readiness;
- stale-cache prevention across deployment and rollback;
- exact identity comparison against the Release Manifest;
- rollback returning the recorded build identity.

These tests must be completed before Release Identity can satisfy Secondary
Deployment Readiness.

## 11. Adoption Sequence

```text
Release Identity specification
    -> build metadata design
    -> artifact identity generation
    -> /api/version additive implementation
    -> local schema/security regression
    -> deployment pipeline integration
    -> Secondary identity validation
    -> rollback identity validation
    -> Primary release-governance adoption
```

Implementation must occur in a separately reviewed change. This specification
does not modify production code or approve Secondary deployment.
